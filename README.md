# Wifi RTT Demo

iPhone을 활용해 실내지도를 제작하고, 실내 좌표를 얼마나 정확하게 계산할 수 있는지 검증하기 위한 데모 프로젝트입니다.

## 프로젝트 목표

- iPhone에서 수집할 수 있는 측정값을 이용해 실내 공간을 지도 형태로 표현합니다.
- 계산된 실내 좌표와 기준 위치를 비교해 위치 측정 정확도를 확인합니다.
- 반복 측정을 통해 오차 범위와 측정 안정성을 기록합니다.
- 5일 안에 핵심 측정 흐름을 구현하고 실제 iPhone에서 검증 가능한 데모를 완성합니다.

## 핵심 검증 항목

- 동일한 위치에서 반복 측정했을 때 좌표 편차
- 기준 위치와 계산 좌표 사이의 거리 오차
- 이동 중 좌표 변화의 연속성과 안정성
- 실내 구조가 지도에 표현되는 방식과 실제 공간의 일치도
- 측정 환경 변화에 따른 정확도 차이

## 목표 개발 기간

총 5일

| 일차 | 목표 |
| --- | --- |
| 1일차 | 요구사항 확정, 측정 방식 조사, 프로젝트 구조 설계 |
| 2일차 | iPhone 측정 데이터 수집 흐름 구현 |
| 3일차 | 실내 좌표 계산 및 데이터 기록 구현 |
| 4일차 | 실내지도 시각화와 측정 결과 연결 |
| 5일차 | 실제 iPhone 반복 테스트, 오차 분석, 결과 정리 |

## 완료 기준

- 실제 iPhone에서 측정 흐름을 실행할 수 있습니다.
- 측정 위치를 실내 좌표로 계산하고 지도에서 확인할 수 있습니다.
- 기준 위치와 계산 결과의 오차를 수치로 기록할 수 있습니다.
- 반복 테스트 결과를 바탕으로 데모의 정확도와 한계를 설명할 수 있습니다.

## 테스트 환경

- 대상 기기: iPhone
- 대상 공간: 실내 테스트 공간
- 목표 산출물: 실내지도, 계산 좌표, 반복 측정별 오차 기록

최소 iOS 18.0, iPhone 전용입니다. ARKit 측정에는 world tracking 지원 실제 기기가 필요합니다.

## RTT 신뢰도 평가

측정 화면 또는 시작 화면의 **실제값 / RTT 입력 및 비교**에서 같은 지점의 좌표를 입력합니다.

1. 지점 이름과 공통 좌표계 ID를 정합니다.
2. 실제 측정 좌표가 있으면 X/Y/Z를 모두 입력합니다. 이 값은 항상 최우선 기준이며 ARKit과 평균하거나 오차 크기로 배제하지 않습니다. 실제 원점 (0, 0, 0)도 유효합니다.
3. 실제값이 없으면 세 칸 모두 비우고 정상 추적 중인 ARKit 좌표를 캡처합니다.
4. 같은 지점에서 얻은 외부 Wi-Fi RTT **위치 계산 결과** X/Y/Z와 측정 시각을 입력합니다.
5. 동일 지점·좌표계 확인 후 저장합니다. 실제값과 ARKit이 모두 없으면 결과만 보존하고 오차 통계에서 제외합니다.

iPhone에서 Wi-Fi RTT를 직접 측정하지 않습니다. Android 또는 외부 RTT 장비의 결과를 수동 입력하거나 JSON으로 가져옵니다. AP별 거리, RSSI, ping 지연시간을 위치 좌표 칸에 넣으면 안 됩니다. AP별 거리로부터 위치를 계산하는 기능과 실시간 외부 기기 연결은 이 패치에 포함하지 않습니다.

모든 값은 **같은 원점·축의 미터 단위 3차원 좌표**여야 합니다. ARKit의 Y는 높이, X/Z는 수평면입니다. 바닥 기준점과 카메라 위치의 높이 차이, RTT 측정 기기와 카메라 사이 센서 위치 차이를 보정해야 합니다. ARKit을 새로 시작하거나 원점을 재설정하면 좌표계 ID가 바뀝니다. ARKit 캡처 후에는 해당 좌표계 ID가 고정됩니다. 실제값 없이 ARKit을 기준으로 쓴 결과는 ARKit 대비 일치도를 의미합니다.

현재 입력 흐름은 **정지 지점 비교**입니다. ARKit 캡처와 RTT 측정 시각을 따로 보존하며, 자동 시간 동기화나 이동 경로 보간은 하지 않습니다. 서로 다른 시간에 움직인 위치를 비교하지 마세요.

- RTT 위치 오차: 선택한 기준 좌표와 RTT 위치 사이의 3차원 거리
- 평균 위치 오차: 비교 가능한 표본들의 위치 오차 평균
- RMSE: 위치 오차 제곱 평균의 제곱근
- 허용 오차 내 비율: 설정한 거리 이하인 표본 수 / 비교 가능한 표본 수
- ARKit 위치 오차: 실제값과 ARKit이 모두 있을 때 두 좌표 사이의 거리

실제값 기준과 ARKit 기준 통계를 분리합니다. 기본 허용 오차 1m는 사용자가 변경하는 평가 조건이며 정확도 보장이 아닙니다. 현재 통계는 저장된 표본 전체를 출처별로 합산하며 추적 실패율이나 RTT 측정 실패율을 나타내지 않습니다.

비교 기록은 앱 내부 JSON에 저장되어 앱 재실행·측정 종료·원점 재설정 후에도 남습니다. **JSON 내보내기**로 파일을 보관할 수 있습니다. 카메라 영상은 저장하지 않습니다.

기록 목록의 **이 기록 편집**으로 실제값을 나중에 추가할 수 있습니다. 수정 저장 시 같은 기록의 기준이 ARKit에서 실제값으로 변경되고 오차와 통계를 다시 계산합니다.

### 외부 결과 JSON 형식

버전 1, 최대 5 MB / 누적 10,000건을 지원합니다. 가져오기는 일괄 검증 후 추가하며 중복 ID나 잘못된 값이 있으면 전체 가져오기를 취소하고 기존 자료를 보존합니다. 날짜는 UTC ISO 8601 형식입니다. 실제값이나 ARKit이 없으면 해당 필드를 생략하거나 null로 지정합니다. ARKit 좌표가 있으면 arkitCapturedAt도 필요합니다.

아래는 파일 형식 설명용 예시이며 실제 측정 자료가 아닙니다.

```json
{
  "version": 1,
  "records": [{
    "id": "01A0424D-C936-4BE2-B6A9-7B10B2F9735C",
    "point": "A",
    "frame": "room-a-origin-1",
    "measuredAt": "2026-09-07T04:00:00Z",
    "actual": { "x": 0, "y": 1.2, "z": -1 },
    "arkit": { "x": 0.02, "y": 1.21, "z": -1.03 },
    "arkitCapturedAt": "2026-09-07T04:00:00Z",
    "rtt": { "x": 0.3, "y": 1.2, "z": -1.4 }
  }]
}
```

외부 장비에서 좌표계를 정렬한 뒤 같은 정지 지점의 기준값과 RTT값을 한 레코드로 구성하세요. 가져온 실제값도 수동 입력과 동일하게 우선합니다.

# 깃 전략

### 태그 컨벤션

`init` : 가장 처음 Initial Commit에 태그 붙이기

`feat` : 새로운 기능 구현 시 사용

`fix` : 버그나 오류 해결 시 사용

`docs` : README, 템플릿 등 프로젝트 내 문서 수정 시 사용

`setting` : 프로젝트 관련 설정 변경 시 사용

`add` : 사진 등 에셋이나 라이브러리 추가 시 사용

`refactor` : 기존 코드를 리팩토링하거나 수정할 시 사용

`chore` : 별로 중요한 수정이 아닐 시 사용

### 커밋 컨벤션

태그는 반드시 **소문자**로 작성합니다.

내용은 한글로 작성합니다.

제목이 **50자**를 넘지 않도록, 간단하게 명령조로 작성합니다. 설명이 필요한 경우 description에 작성합니다.

```markdown
[feat] 로그인 기능 구현
```

### 브랜치 컨벤션

태그/#이슈번호-작업하는 파일

```markdown
feat/#1-loginUI
```

### 브랜치 전략

`main` : 출시(release)에 사용하는 브랜치입니다.

`develop` : 개발된 기능들을 최종적으로 합쳐서 확인하는 브랜치입니다.

- 기본 브랜치이며 개발을 마친 후에 반드시 develop에 머지합니다.
- 개인 브랜치에서 작업을 마치면, 개인 브랜치에서 develop 브랜치를 머지한 후에 develop에 pull request를 요청합니다.

`feature` : 태그를 붙이는 모든 브랜치들을 말합니다. 기능 개발, 버그 수정 등을 반드시 이 브랜치에서 진행해주세요.
